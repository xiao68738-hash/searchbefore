# 產銷履歷（TAP）系統串接 — 路線圖

本文件是「把 App 的田間紀錄直接上傳到產銷履歷系統」這件事的**單一參考點**。對應待辦 **串接-3**。

**目前狀態：卡在資格與規格，尚未開工。** 這不是技術做不到，而是規格與代碼表要通過官方審核才拿得到。本文件記錄卡在哪、要解卡需要什麼、解卡後怎麼做。

## 二、為什麼現在難（三個實際阻塞）

### 1. 傳輸方式是 SOAP，純前端打不到
凌網科技（Hyweb，TAP 系統承包商）2026-07-17 回覆：介接為 **Web Service（SOAP）+ XML**，走 L4→L3。

噴前查目前是**純靜態前端**（GitHub Pages + Firebase），沒有後端。要串接就必須新增一個**後端代理**負責認證與 XML 組裝——這會第一次讓這個專案有伺服器端，連帶產生維運、成本與個資責任。

### 2. 官方代碼表要「審核通過」才拿得到
TAP 欄位以**官方代碼**為主，不吃自由文字。作物、品種、作業內容、肥料／防治／其他資材、防治對象全部要從自由文字轉成官方代碼，而**代碼表本身也是透過 API 下載**（作物代碼下載、品種資料下載、資材下載…），要審核通過才給。

> **這是最大的一塊，也是最不能亂猜的一塊。** 在拿到真正的代碼表前，不要為了「先做起來放」而自訂一套對應——猜錯會讓農友把錯的資料上傳到官方系統，那是無法悄悄回收的。

### 3. 驗證主體是「農戶」不是「App」
產銷履歷的驗證與登錄主體是個別農戶／團體。尚未確認的關鍵問題：
- 每位農友是否需**各自**申請 API 資格與憑證？
- 有沒有**沙箱／測試環境**與 WSDL 可先行開發？
- 第三方 App 代為上傳的身分怎麼帶（代操作？授權？）

這三題沒答案之前，架構怎麼設計都是空談。

## 三、解卡需要什麼（實際步驟）

> 這段多半**需要你出面**，我做不了：申請與洽談都要以經營者／驗證農戶身分進行。

1. **確認自身資格** — 是否已（或打算）取得產銷履歷驗證。未取得驗證就沒有上傳對象。
2. **向農糧署／凌網詢問下列四題**（建議一次問完，這也是本文件最該被更新的部分）：
   - 第三方工具代農戶上傳的**授權方式**為何？
   - 是否提供**沙箱環境／WSDL／介接規格書**供開發前測試？
   - 代碼表（作物、品種、資材、防治對象）**取得方式與更新頻率**？
   - 申請流程、審核時程與必要文件？
3. **取得規格後回填本文件**，再重新評估工作量與是否值得做。

## 四、解卡後的實作順序（草案，待規格確認）

| 階段 | 內容 | 前置 |
|---|---|---|
| S1 | 依規格書重寫本文件第二節，確認架構可行 | 拿到規格 |
| S2 | 建立**代碼對照層**：官方代碼 ↔ App 現有自由文字（作物、資材、防治對象） | 代碼表 |
| S3 | 後端代理（認證 + SOAP/XML 組裝），先只支援**單向上傳單一表**（建議從表7 用藥紀錄開始，欄位最完整） | S2 |
| S4 | App 端「上傳」UI：**逐筆確認制**，絕不自動批次送出 | S3 |
| S5 | 沙箱全流程測試 → 小規模實地試用 → 正式 | S4 |

### 設計原則（現在就先定下來）
- **上傳一律逐筆人工確認**，不做背景自動同步。上傳到官方系統是**對外行為**，錯了不是改一改就好。
- **對不到官方代碼就擋下來**，明白告訴使用者「這筆需要人工處理」，不用近似代碼硬湊。
- **安全採收日等估算值不上傳**，或明確標為參考值——本工具的估算不能變成官方紀錄的依據。
- 維持既有紅線：**不得宣稱本工具可代為申報、通過驗證或保證合規**。

## 五、在那之前的替代方案（已上線）

TAP 登打對照表匯出已經能讓農友省下「翻本子、逐欄想」的時間，只是仍需人工謄打。若要在阻塞期間再改善，成本最低的方向是：

- 依實際使用回饋，調整對照表欄位順序或補欄位（例如使用量／施藥面積）。
- 匯出檔加上「本表僅供謄打參考」的既有註記維持不變。

## 六、風險提醒

一旦真的開通上傳，這個 App 就從「查詢與自主紀錄輔助」變成**會影響官方紀錄的工具**，責任層級不同。屆時隱私權政策、免責聲明與 Play 資料安全表單都要重新檢視（現行說明是「資料只存在裝置／你的 Google 帳號」，上傳官方系統不在其涵蓋範圍內）。
