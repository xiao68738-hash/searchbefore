# 產銷履歷（TAP）協作試辦與 L3 串接路線圖

本文件是產銷履歷相關工作的**單一參考點**，分開管理兩件不同的事：

- **待辦 #34：L3 API 直傳**——仍受官方資格、規格及代碼表阻塞。
- **待辦 #35：資訊服務專員協作試辦**——不必等 API，可先驗證農民留資料、專員覆核與人工登打的流程。

**目前狀態：#35 已開始內部基礎作業；#34 尚未開工。正式前端不顯示協作、OCR 或 L3 功能。**

更新日期：2026-08-01　｜　欄位細節見 [TGAP欄位對照.md](TGAP欄位對照.md)

## 一、產品定位

噴前查不應以「取代登打員」為目標。現階段最適合的角色分工是：

> 農民留下現場事實 → 噴前查整理成草稿 → 資訊服務專員檢核、補漏與對應代碼 → 專員在官方 L3 完成正式登打

本次試辦希望驗證：資訊服務專員是否能減少重複抄寫，把時間移到資料品質管理、例外處理與農民輔導。這只是產品假設，不代表主管機關已接受新的職務或補助模式。正式送出與責任仍由人掌握；任何 OCR 或規則判斷都不能自動寫入官方系統。

「資訊服務專員」與產銷履歷「輔導員」不是同一職稱。訪談、試辦及文件中必須確認對方實際身分，不可混稱。

## 三、官方已確認與仍待確認

### 已由目前書面往來確認

1. 生產階段介接採 Web Service（SOAP）與 XML，方向為 L4→L3。
2. 申請時需提供一位已通過驗證、具 L3 組織代碼的農產品經營者作為測試對象。
3. 系統完成開發與介接測試後，其他具 L3 組織代碼的經營者原則上可使用，不需逐一重提同一套系統介接申請。
4. 尚未通過驗證者也可能具 L3 使用資格；是否可操作仍以其組織代碼與官方權限為準。
5. 規格文件、WSDL 與測試環境需先通過申請才提供。
6. 作物、品種、作業、肥料、資材及防治對象等代碼由 API 取得，不能自行猜測建立。
7. 原則上所有需要使用的下載、維護、刪除及產季結束 API 都要提出申請，實際開放項目由農糧署審核。

### 必須取得農糧署書面答覆

1. 核准的第三方 API 紀錄，能否帶入實名綁定的資訊服務專員身分？
2. 經專員覆核後由 API 建立的紀錄，是否計入「每 20 筆有效資料換算 1 小時」的補助筆數？
3. 農民建立草稿、專員確認送出時，官方認定的登打人與登打時間為何？
4. 多批次共同作業、批次上傳、修改、刪除及逾期更新，如何計算有效筆數與 7 個工作日期限？
5. 第三方系統必須保存或傳送哪些稽核資料，例如來源系統、確認人、確認時間、修改歷程與官方回執？
6. API 測試環境能否測試資訊服務專員實名綁定及筆數歸屬？

在第一、二題得到肯定且可實測的答覆前，不承諾「使用噴前查不影響專員補助」。

參考：[115年度產銷履歷農糧產品驗證費用補助作業須知](https://orgws.kcg.gov.tw/001/KcgOrgUploadFiles/10/RelFile/7312/517796/5b9e87b9-3aaa-46a2-992e-41e9b0464985.pdf)

## 五、8 週試辦設計

### 參與者

- 1 位已通過驗證並具 L3 組織代碼的農產品經營者。
- 1 位已完成實名綁定的資訊服務專員。
- 5～10 位願意配合的農民。
- 先聚焦 1～2 種真實紀錄表，不做任意文件辨識。

### 預定試辦流程（35E 完成後）

1. 農民先用紙本、拍照或極簡表單留下原始資料；語音屬後續方向，第一輪不把它當必要條件。
2. 噴前查整理為「未確認草稿」。
3. 專員查看原始依據、缺漏、低信心欄位及版本差異。
4. 資料不完整時退回補充；不得以猜測補值。
5. 專員確認後，仍依現行官方流程人工登打。
6. 系統只能記為「專員已標記完成登打，噴前查尚未向官方系統查證」，不能顯示已上傳、已受理或已核准。

### 每週量測

- 每筆資料從取得到完成登打的總時間。
- 每 100 筆需要回頭詢問農民的次數。
- 必填欄位缺漏率、修正率與重複資料率。
- 辨識結果中低信心或錯誤欄位比例。
- 作業發生後 7 個工作日內完成的比例。
- 專員可認列的有效筆數及收入是否受影響。
- 農民能否在沒有開發者陪同下完成資料留存。

### 停止條件

- 試辦會讓專員的有效筆數或補助收入受損，且沒有透明補償或制度解法。
- 低信心、缺漏或矛盾資料仍可直接進入正式紀錄。
- 無法清楚追溯原始資料、修改版本、確認人及時間。
- 農民必須操作比原流程更多的步驟，或大量需要開發者在場協助。
- 涉及未經同意的跨帳號資料分享。

## 六、已開始的內部基礎

`tap-workflow.js` 目前只是一個**未發布、未連線、無 UI 的純狀態模型**，用來先固定安全語意：

```text
draft → awaiting_review → needs_changes → awaiting_review → internal_review_complete
```

- 原始紀錄改動時版本加一，舊的覆核結果立即失效。
- 舊版本曾由專員提出的人工登打聲明會保留在 `externalEntryClaims`，後續修訂或取消也不能抹除；必要時標記仍需處理外部紀錄。
- 現階段 L3 互動狀態只允許 `not_connected`、`manual_entry_claim_pending`、`manual_entry_claim_recorded_unverified`。
- `manual_entry_claim_recorded_unverified` 只代表專員自行提出聲明，並不代表噴前查已向 L3 查證。
- 在取得真正 API 回應及官方回執前，禁止建立 `submitted`、`accepted` 或類似狀態。
- 角色與能力不能只靠前端自行宣稱；`actor.role/capabilities` 只可接受可信任後端產生的情境，未來必須由 Firebase UID、工作區邀請與後端權限共同核發。
- 目前狀態必須能由事件白名單依序重播得到；缺少送審或內部覆核事件時，不能只改欄位偽造成完成。快照指紋只防版本錯置與意外竄改，不是安全簽章。
- 目前的內嵌事件只是流程歷史，不是不可竄改的正式稽核紀錄；試辦前必須改成伺服器端追加式事件。
- 這個檔案不在 `index.html`、Service Worker 或正式 build 清單內。

現行 Google 雲端同步是單一帳號擁有者模型，不適合專員在同一台電腦切換處理多位農民。開放協作前必須另建工作區權限、逐次分享同意、不可竄改的事件紀錄，並更新隱私政策。

## 七、OCR 與正式前端紅線

1. `formOcr` 維持 `hidden`；未完成 Android 正式整合、實機品質校正及完整驗收前，不建立前端入口。
2. 若安排指定測試者，狀態才可改為 `development`，入口、標題及主要操作都要標示「開發中」。
3. OCR 結果永遠是未確認草稿，不自動儲存、不自動上傳。
4. 原始照片預設留在裝置內；不得把 Base64、照片 URI 或影像混入網頁草稿。
5. 日期、作物、田區、藥劑、稀釋倍數、用量與安全採收期等關鍵欄位必須逐欄確認。
6. 用藥內容只有在作物、防治對象與藥劑能唯一對回正式登記資料時，才可帶入原紀錄表單。
7. Android App 只可顯示不附帶任何內容、功能或權益的綠界純自願支持；未來 App 內數位功能仍保留給 Google Play Billing。

詳見 [前端功能發布規則.md](前端功能發布規則.md) 與 [Android OCR正式整合.md](Android%20OCR正式整合.md)。

## 八、取得正式規格後的實作順序

1. 依核准文件確認權限、憑證、代碼表與補助筆數歸屬。
2. 建立伺服器端秘密管理及官方代碼同步；API 憑證不得進瀏覽器、Firebase 公開設定或 App 套件。
3. 先支援單一紀錄類型、單一測試組織及逐筆人工確認。
4. 沙箱測試建立、修改、刪除、逾期、重複送出與錯誤回應。
5. 保存來源版本、確認者、時間與官方回執，且不可由客戶端竄改。
6. 完成資安、隱私、備援、刪除與責任說明後，才可進行小規模正式試辦。

一旦開通 L3 上傳，噴前查就從自主紀錄工具變成會影響官方紀錄的系統。屆時隱私權政策、Play 資料安全表單、後端維運與事件處理程序都必須重新審查。
