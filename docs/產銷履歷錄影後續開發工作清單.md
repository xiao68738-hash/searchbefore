# 產銷履歷錄影後續開發工作清單

> 基準日期：2026-08-09
> 事實來源：[`產銷履歷系統錄影-操作流程與欄位地圖.md`](./產銷履歷系統錄影-操作流程與欄位地圖.md)
> 原則：先把紙本內容變成可核對的噴前查草稿，再談 L3 代碼映射與 API 上傳；未取得官方規格的功能不得假裝已完成串接。

## 1. 這一階段的產品邊界

噴前查目前要解決的是：

1. 農民或登打員可以一次選取多張照片。
2. 系統先判斷文件用途，再從一張照片整理零筆、一筆或多筆候選草稿。
3. 每筆草稿保留原圖、來源照片、辨識文字與不確定欄位，讓使用者快速核對。
4. 經人工確認後，只帶入噴前查既有表單；不自動儲存、不自動上傳 L3。
5. 取得官方 API 字典後，再增加 L3 代碼映射、上傳前檢核與送出功能。

這一階段不做：

- 不複製整套 L3 驗證申請、商品審核與標籤列印後台。
- 不把自我查核表的勾選結果當成生產紀錄。
- 不把資材入出庫表誤當成一次施肥或一次購入。
- 不因 OCR 看見一個名稱，就自行猜成正式農藥、肥料、作物或 L3 代碼。
- 不宣稱辨識結果可直接送農糧署。

## 2. 文件路由矩陣

OCR 在抽欄位前，先將每張照片分到以下用途；信心不足時讓使用者選擇，不硬猜。

| 路由 | 文件例子 | 使用者得到的結果 | 目前可否帶入噴前查 | L3 狀態 |
|---|---|---|---|---|
| `production-record` | 用藥、施肥、一般栽培、採收、採後處理 | 一筆或多筆待確認作業草稿 | 可以，但仍須在原表單再次確認 | 等待正式代碼映射 |
| `supporting-record` | 器具／機械／設備保養維修 | 多筆本機設備管理草稿 | 可以存成本機輔助紀錄 | 是否屬 L3 上傳範圍待確認 |
| `material-ledger` | 肥料／資材入出庫表 | 資材主檔候選＋多筆庫存異動草稿 | 僅供本機整理或匯出 | 不視為單筆生產作業；API 範圍待確認 |
| `reference-only` | 生產及出貨自我查核表 | 顯示原文、日期與查核者候選，可略過 | 不建立田間紀錄 | 農友回饋為現場備查，非 L3 日常登打 |
| `master-data` | 農戶基本資料、田區／地籍資料 | 主檔候選，逐欄確認 | 暫不自動寫入個資或田區 | 等待主檔 API 與權限規格 |
| `admin-output` | 驗證申請、商品資料、標籤列印清單 | 僅辨識／說明，不建立生產紀錄 | 不提供自動帶入 | 屬高權限後台，暫不開發 |
| `unknown` | 無法判斷、混合頁面、照片背景文字過多 | 原圖＋原文＋人工選擇用途 | 不自動帶入 | 不做任何上傳推定 |

## 3. P0：現在就要完成

### P0-1 固定文件路由與安全邊界

- [x] 在 OCR 草稿加入 `route`、`destination`、`l3MappingStatus` 與 `reason`。
- [x] 明確路由至 `reference-only`、`master-data` 或庫存／設備專用流程時，不得通過一般作業 `canCommit`；證據不足或同分時改由人工確認用途。
- [x] 設備紀錄顯示「本機輔助紀錄；是否可上傳 L3 待確認」。
- [x] 資材庫存顯示「庫存帳；不是一次施肥，也不直接送 L3」。
- [x] 自我查核表維持可略過，不要求使用者逐列整理。

驗收：同一份 OCR 文字無論從哪個入口進入，都不會把查核表、基本資料或標籤畫面誤存為田間作業。

### P0-2 多照片、多列與來源追溯

- [x] 每張照片先有獨立 `queued`、`processing`、`recognized`、`failed` 狀態與固定來源順序；草稿不保存原圖、Base64 或 Object URL。
- [ ] 補齊「已略過／已帶入」狀態，並讓每一個欄位候選直接連回 `sourceImageId`、頁次、文字區塊及座標。（目前已完成草稿層來源與 block／word 幾何。）
- [ ] 一張照片可產生多筆；多張照片不得把不同頁的日期或資材錯配在一起。
- [ ] 使用者可隨時開原圖、上一張／下一張、排除一筆及新增漏掉的列。
- [x] 單張失敗不影響其他照片，失敗項仍保留在逐張核對列並可查看原圖。
- [ ] 增加只重試失敗單張的按鈕與重試次數／錯誤狀態。

驗收：混合上傳設備表、肥料庫存表及查核表時，三張照片各自得到正確用途，不會合併成一筆草稿。

### P0-3 生產紀錄的標準草稿模型

目前已先完成各紀錄類型的必要欄位驗證，並把「可帶入人工整理」與「可正式儲存」拆成兩道門檻。以下主表＋多筆明細模型仍待完成。

共同欄位：

- 作業日期或起訖日期。
- 作物／品種與栽培批次候選。
- 田區／地籍候選。
- 作業種類、作業內容。
- 執行人、備註、原圖證據與人工確認狀態。

明細欄位：

- 用藥：多筆農藥、用量、水量、稀釋倍數、防治對象、安全採收期。
- 施肥：多筆肥料、用量、水量、施肥方式。
- 採收：批次、單日公斤數、儲藏場所。
- 採後處理：處理方式、處理前後重量、驗證狀態。
- 一般栽培：作業內容、方法／設備與必要備註。

驗收：不得再以一組「資材／數量」欄位假裝涵蓋所有紀錄類型；同一作業可有多筆資材明細。

### P0-4 建立可量測的測試資料集

- [ ] 使用已取得同意且移除不必要個資的真實照片。
- [ ] 依文件類型至少各建立清楚、歪斜、跨頁、背景干擾與手寫樣本。
- [ ] 人工建立正確答案，不用 OCR 自己的輸出當標準答案。
- [ ] 計算文件分類正確率、必要欄位正確率、漏欄率、人工修改數與總處理時間。
- [ ] 個資、照片與完整辨識文字不放入公開 GitHub。

第一階段通過條件：

- 高風險文件路由不可發生「備查文件誤存成生產紀錄」。
- 用藥正式藥劑仍須唯一對回官方登記資料。
- OCR 輔助後的總時間確實低於完全人工登打。

### P0-5 L3 映射占位，但不假裝已串接

- [ ] 草稿欄位與 L3 欄位／代碼分開保存。
- [ ] 尚未取得代碼時顯示 `unmapped`，不得拿畫面文字自行編碼。
- [ ] 建立映射錯誤、字典版本與人工選擇的稽核欄位。
- [ ] 上傳按鈕持續隱藏，直到取得測試環境、API 字典與錯誤碼。

## 4. P1：P0 穩定後

- [ ] 取得 API 後，下載並快取作物、品種、作業種類、作業內容、肥料、防治對象等正式字典。
- [ ] 完成採收與採後處理的專用覆核介面。
- [ ] 將組織、成員、栽培批次、田區／地籍與倉儲場所做正式映射。
- [ ] 增加草稿重複偵測，避免同一照片或同一作業重複建立。
- [ ] 建立登打員批次核對模式：鍵盤操作、批次套用共同欄位、一次處理多張但逐筆確認。
- [ ] 建立 OCR 成本、失敗率與省工時間報表，內容不得含照片或完整辨識文字。

## 5. P2：取得正式資格與真實需求後

- [ ] L3 測試環境上傳、修改、刪除與產季結束流程。
- [ ] 上傳佇列、斷線重試、冪等鍵、衝突處理及稽核日誌。
- [ ] 多人角色與權限：農民、登打員、管理者、只讀協作者。
- [ ] 驗證範圍與商品主檔的唯讀同步。
- [ ] 標籤資料準備；除非取得正式規格、權限及設備，不做直接列印。

## 6. 暫緩或移除的工作

| 項目 | 決定 | 原因 |
|---|---|---|
| 把自我查核表全部轉成可編輯勾選表 | 暫緩 | 農友回饋為核檢時查看紙本，不是日常 L3 登打；投入大、直接省工價值低 |
| 直接從 OCR 原文建立正式 L3 紀錄 | 禁止 | 缺正式代碼、角色與 API 規格，錯誤責任高 |
| 在首頁增加大量 OCR／L3 入口 | 不做 | OCR 仍是受驗證碼限制的測試功能，不能讓一般使用者誤以為已正式串接 |
| 複製驗證申請與商品審核後台 | 暫緩 | 不是農民日常記錄的主要省工點，且屬高權限流程 |
| 直接印履歷標籤 | 暫緩 | 依賴專用程式、瀏覽器、設備、張數扣除與補印／作廢稽核 |
| 以採收量自動計算全部標籤需求 | 禁止 | 實際貼標量受通路、品質與成本影響，不等於總採收量 |

## 7. 建議執行順序

1. 完成 P0-1 路由與不可誤存測試。
2. 補 P0-2 的來源照片／區塊追溯與逐張重試。
3. 將用藥、施肥、採收、採後處理拆成明確的標準草稿。
4. 用真實樣本量測分類、欄位與省工時間。
5. 與已驗證農產品經營者完成申請，取得官方 API、代碼字典與測試環境。
6. 才開始 L3 映射與上傳；標籤列印另立專案評估。

## 8. 完成定義

此清單的 P0 完成時，使用者應能：

- 一次選多張不同類型文件。
- 清楚知道每張照片被判定為什麼用途。
- 得到零筆、一筆或多筆可核對草稿。
- 隨時查看原圖、修正欄位、略過不需要的文件。
- 確定任何結果都不會在未確認下儲存或上傳。
- 看得懂哪些資料只是本機整理，哪些未來才可能對應 L3。
