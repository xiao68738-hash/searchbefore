# OCR 跨列欄位共識提示

日期：2026-09-09；對應 OCR-06／OCR-09 的結構候選管線。這是本機程式與測試更新，沒有發布 APP、沒有送出照片，也沒有把私人圖片加入版控。

## 目的

Google Cloud Vision 回傳單字方框，不保證同一欄在不同列使用相同索引。後端現在會在同一頁、同一照片區域內，以候選格中心點做保守的一維幾何分群，為現有 `cellCandidates` 加上：

- `columnIndex`：僅為由左至右的幾何索引；
- `columnSupport`：在同頁／同區域出現於該索引的列數；
- `columnCountEstimate`：該區域的欄位數估計；
- `layout.columnAlignment = geometry-consensus-v1`。

此步驟不新增、刪除、拉伸或填寫任何儲存格，也不推測「日期」「藥劑」等語意。欄位提示仍須對照原圖與人工確認；若候選欄位過多（超過 40），會省略提示而不製造欄位地圖。

## 驗證

- Python 語法檢查通過。
- 兩列、兩欄的合成幾何案例通過：同欄索引一致、支援列數正確。
- `form-ocr-ui.test.js` 通過：合法提示可接收，超界索引／支援數會拒絕。
- 全專案既有 JavaScript 測試通過；此功能不會把圖片、token 或原始檔名帶入草稿。
- 已將使用者確認的表13欄位（資材名稱「蘇力菌」、日期「7/14」）建立 1 筆本機去識別化校正紀錄；彙整結果為日期 1/1 exact、資材名稱 0/1 exact 且有 1 個候選。檔案僅在 `D:/SearchBefore/private/ocr-corrections`，不會自動上傳。

## 與 50% 目標的關係

這是版面判斷的可追溯性改善，不是文字辨識率提升，也不能把歷史 NAF cell F1 直接提高到 50%。目前未觸碰的 21 份留出資料，區域格線補救後 cell F1 為 23.69%；真實表13照片的 Windows 繁中 OCR 仍未讀出手寫「蘇力菌」與「7/14」。因此暫不接入自動填表或正式版數據宣稱。
