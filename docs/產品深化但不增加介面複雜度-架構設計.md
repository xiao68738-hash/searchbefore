# 產品深化但不增加介面複雜度：架構設計

更新日期：2026-08-07  
狀態：設計稿，尚未接入正式前端

## 一、這次要解決的問題

噴前查目前已能保存田區、用藥、栽培、施肥、採收、採後處理、資材購入與設備紀錄，但使用者仍需自己打開不同頁面，才能理解「這塊田最近做了什麼、目前能不能採、下一步要去哪裡處理」。

這次不再增加一個新的主功能，也不擴充 OCR。目標是利用現有資料，在原本的紀錄入口內多做一層整理，讓產品從「保存紀錄」深化為「協助回顧與判讀」。

設計底線：

- 底部導覽維持六項，不新增分頁。
- 紀錄首頁仍維持田區、作業、整理三個入口。
- 首畫面最多增加一張摘要卡，不把所有資訊同時攤開。
- 不宣稱符合產銷履歷、有機驗證或主管機關要求。
- 不替使用者決定可以採收；只重述已保存資料與安全採收期計算結果。
- 資料不足時明確顯示「無法判定」，不以猜測補值。

## 二、核心架構

```text
現有本機資料
├─ fieldPlots：田區／種植批次
├─ records：用藥紀錄
└─ farmRecords：其他農務與設備紀錄
        │
        ▼
田區資料整理層（新增，純計算、不改原始資料）
├─ 合併時間軸
├─ 安全採收狀態
├─ 最近一次作業
├─ 紀錄分布
└─ 資料異常／缺口
        │
        ▼
行動建議層（規則式、可追溯）
├─ 先建立田區
├─ 補上無法判定的採收期
├─ 查看仍在停採中的田區
├─ 繼續記錄目前田區
└─ 匯出既有紀錄
        │
        ▼
現有紀錄首頁的一張摘要卡
└─ 點擊後才進入既有田區詳細頁或既有功能
```

這一層只讀取現有資料並產生衍生結果，不回寫或修改原始紀錄。即使摘要演算法發生問題，原始紀錄仍然保留。

## 三、新增的資料整理結果

建議新增 `field-summary.js`，對外只提供一個主要函式：

```js
buildFieldSummary({ fieldPlots, pesticideRecords, farmRecords, activePlotId, today })
```

回傳內容：

```js
{
  selectedPlot: {
    id: "plot-id",
    name: "番茄・A區",
    crop: "番茄"
  },
  totals: {
    plots: 2,
    pesticideRecords: 5,
    farmRecords: 8
  },
  latestActivity: {
    date: "2026-08-06",
    type: "fertilizer",
    label: "施肥"
  },
  harvestSafety: {
    status: "waiting", // safe | waiting | unknown | none
    safeDate: "2026-08-12",
    daysRemaining: 5,
    reason: "2 筆用藥紀錄合併後的最晚可採日"
  },
  attention: [
    {
      code: "MISSING_PHI",
      level: "warning",
      label: "有 1 筆用藥缺少安全採收期",
      target: "countdown"
    }
  ],
  nextAction: {
    code: "REVIEW_UNKNOWN_PHI",
    label: "先核對缺少的安全採收期",
    target: "countdown"
  }
}
```

`field-summary.js` 不儲存新的個人資料，也不呼叫網路。每次開啟紀錄首頁時，依目前裝置上的資料即時計算。

## 四、田區選擇規則

摘要卡一次只呈現一個田區，避免資訊過滿。選擇順序如下：

1. 使用者已設定的預設田區 `activePlotId`。
2. 若沒有預設田區，選擇最近有作業紀錄的田區。
3. 若所有田區都沒有紀錄，選擇最近建立的田區。
4. 完全沒有田區時，顯示「先建立第一個田區」。

第一版不增加田區切換器。使用者點「查看田區」後，沿用現有田區管理頁選擇其他田區。

## 五、安全採收狀態

沿用現有 `safety.js` 的日期計算，不另做第二套規則。

同一田區的判斷順序：

1. 只納入能明確連到該田區的用藥紀錄。
2. 每筆紀錄分別計算可採收日。
3. 有多筆用藥時取最晚可採收日。
4. 只要其中一筆缺少安全採收期，就顯示 `unknown`，不得顯示「可採收」。
5. 沒有用藥紀錄時顯示 `none`，文字為「目前沒有可連動的用藥紀錄」，不得顯示安全或不安全。

顯示文字限定為：

- `waiting`：仍在停採期，預估最早可採日期為 YYYY/MM/DD。
- `safe`：依目前保存的紀錄，停採倒數已結束；採收前仍需核對產品標示。
- `unknown`：有用藥資料不足，現在無法判定可採日期。
- `none`：目前沒有可連動的用藥紀錄。

## 六、行動建議規則

建議只顯示一個，避免首頁變成待辦清單。優先順序由高到低：

| 優先 | 條件 | 顯示內容 | 前往既有位置 |
|---|---|---|---|
| 1 | 沒有田區 | 先建立第一個田區 | 田區新增／管理 |
| 2 | 有用藥缺少安全採收期 | 先核對無法判定的用藥紀錄 | 安全採收倒數 |
| 3 | 仍在停採期 | 查看最晚可採日期 | 安全採收倒數 |
| 4 | 田區尚無任何紀錄 | 為這個田區留下第一筆作業 | 農務與設備紀錄 |
| 5 | 已有資料 | 繼續記錄這個田區 | 農務與設備紀錄 |
| 6 | 有可匯出資料 | 整理或匯出現有紀錄 | 用藥歷史／匯出 |

這些是操作導引，不是農務建議。系統不應自行建議施肥、施藥或採收。

## 七、介面呈現原則

正式實作時，只在 `recordHubHome` 的三個既有入口上方加入一張摘要卡：

```text
番茄・A區                         查看田區 ›
最近作業　8/6 施肥
停採狀態　還有 5 天，8/12 起可採

[先查看最晚可採日期]
```

限制：

- 平時只顯示田區名稱、最近作業、安全狀態與一個按鈕。
- 不在卡片內放六種紀錄統計、完整時間軸或多個匯出按鈕。
- 詳細的作業鏈、抗藥性風險與時間軸仍留在現有田區詳細頁。
- 沒有田區時，摘要卡改為簡短的第一次使用引導，不再額外顯示教學框。
- 深色模式、高對比與字體大小沿用現有設定。

## 八、與既有程式的整合點

正式開發預計只動以下位置：

- `field-summary.js`：新增純計算模組。
- `tests/field-summary.test.js`：測試田區選擇、安全狀態與建議優先序。
- `index.html`：加入摘要卡容器與渲染函式。
- `tests/index-syntax.test.js` 或新增 UI 測試：確認摘要卡不影響原本三個入口。

優先重用：

- `PQC_FARM.buildTimeline()`：合併用藥與農務時間軸。
- `PQC_FARM.recordCoverage()`：統計既有紀錄分布。
- `PQC_SAFETY.safeHarvestDate()` 或既有群組倒數邏輯：計算可採日期。
- `activePlotId`、`plotById()`、`recordsForPlot()`：維持目前田區連結方式。

不要把摘要結果寫入 `localStorage`，避免形成另一份可能過期的狀態。

## 九、測試情境

至少涵蓋以下情境後才可接前端：

1. 完全沒有田區。
2. 有田區但沒有任何紀錄。
3. 有多個田區但未設定預設田區。
4. 預設田區已被刪除。
5. 同一田區有多筆用藥，取最晚可採日。
6. 同一田區有一筆用藥缺少安全採收期。
7. 用藥紀錄只有作物名稱、沒有田區 ID，不可錯連到同作物的多個田區。
8. 有農務紀錄但沒有用藥紀錄。
9. 未來日期、無效日期或損壞的舊資料。
10. 深色模式、特大字與窄螢幕下仍只呈現一張卡與一個主要按鈕。

## 十、分階段啟用

### 階段一：只做計算與測試

- 建立 `field-summary.js` 與單元測試。
- 不接正式畫面。
- 用現有假資料驗證規則是否會誤判。

### 階段二：接入紀錄首頁

- 只顯示一張摘要卡。
- 不增加設定開關，不改底部導覽。
- 先標示「依目前裝置紀錄整理」。

### 階段三：真實使用驗證

觀察農民或登打員是否能更快回答三個問題：

1. 我現在正在看哪一塊田？
2. 最近一筆紀錄是什麼？
3. 下一步要按哪裡？

若摘要卡沒有降低尋找時間，應刪除或縮減，不再增加更多資訊。

## 十一、這一輪刻意不做

- 不擴充 OCR 文件類型、模型或 AI 整理。
- 不建立農務自動建議或施藥推薦。
- 不建立新的主選單、儀表板或通知中心。
- 不把查核表誤當成 L3 必須登打的生產紀錄。
- 不宣稱紀錄完整就等於通過驗證。
- 不將摘要結果上傳雲端。

這套架構的價值是把既有功能連成可理解的狀態，而不是再增加使用者需要學習的功能數量。
