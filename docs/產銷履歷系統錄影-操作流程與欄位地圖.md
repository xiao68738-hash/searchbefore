## 1. 標記規則

- `已確認`：影片畫面或音訊直接呈現。
- `推論`：依畫面流程整理出的合理解釋，但影片沒有直接說明。
- `待確認`：畫面模糊、音訊不清楚、權限不足或尚未看到。
- `不適用`：屬於驗證查核表、內部稽核或其他不需登打進 L3 的資料。

任何欄位映射都必須附上來源時間點；沒有時間點的內容只能列為待確認。

### 5.2 欄位關係

後續至少要補齊以下關係：

- 組織 → 經營者／成員
- 田區 → 作物／品種
- 產季或栽培批次 → 生產紀錄

- 防治作業 → 病蟲害對象／農藥代碼
- 施肥作業 → 肥料代碼
- 組織／使用者 → 資材主檔 → 登記來源／自製來源 → 常用量／購入紀錄
- 農藥正式識別碼 → 商品名／普通名稱／有效成分／許可證等多種搜尋別名
- 採收 → 日期／數量／批次或履歷編號
- 採後處理 → 處理方式／重量／驗證狀態
- 採收 → 商品主檔／包裝規格 → 標籤申請 → 實際列印／作廢／補印與稽核軌跡

這些只是待查清單，不代表影片已證明系統一定採用此結構。

## 7. 與噴前查的對應

### 7.1 可以直接重用

- 田區與種植批次的本機資料模型。
- 用藥、一般田間作業、採收與資材相關草稿。
- OCR 的多圖片佇列、逐筆確認與不自動儲存原則。

### 7.2 必須補上的中介層

噴前查不應把 OCR 原始文字直接當成可上傳資料。正確路徑應是：

`照片／人工輸入 → 候選草稿 → 人工確認 → 噴前查標準欄位 → L3 代碼映射 → 上傳前檢核 → API`

待影片確認的重點：

- 每個畫面實際要求哪些固定代碼。
- 同一張表格能否產生多筆紀錄。
- 哪些欄位可留白、哪些欄位缺少就不能送出。
- 修改、刪除、產季結束是否有不可逆影響。

## 8. OCR 對應原則

1. 先判斷文件類型，再抽取多筆紀錄，最後才映射到系統欄位。
2. 印刷文字、手寫內容、勾選框與表格座標要分開保存，不可只留合併後全文。
3. 一張照片可產生零筆、一筆或多筆候選草稿。
4. 低信心欄位必須逐欄確認；不得因辨識到表格標題就自動上傳。
5. 不屬於 L3 登打範圍的查核表，要顯示「供查核，不建立生產紀錄」。
6. 影片確認到的欄位名稱與代碼規則，才可成為正式映射依據。

## 10. 低記憶體續作方式

後續作業固定遵守：

1. 影片以本機磁碟串流方式讀取，不載入整部檔案。
2. 每次只處理約 2–5 分鐘。
3. 每段最多抽取少量關鍵畫面與低位元率音訊。
4. 該段整理完成後立即刪除暫存片段或覆寫，不累積大量素材。
5. 先把確認結果寫入本文件，再繼續下一段。
6. 中斷後從本文件最後一個已完成時間點續作。
7. 大型原始影片、音訊與影格不得提交到 GitHub。

## 11. 開發直接結論

1. 噴前查第一階段應聚焦「查詢、計算、日常生產紀錄、人工確認與可攜匯出」，不要複製整套 L3 驗證管理、商品審核與標籤列印後台。
2. OCR 正式資料路徑固定為：`照片／人工輸入 → 文件分類 → 零至多筆候選草稿 → 逐欄人工確認 → 噴前查標準欄位 → L3 代碼映射 → 上傳前檢核 → API`。
3. 生產作業要採主表＋多筆資材明細；同一張照片及同一次作業都可能產生多筆藥劑、肥料、採收或設備紀錄。
4. 作物、品種、成員、田區／地籍、資材、倉儲、商品與包裝是主檔；作業、購入、採收、庫存異動與標籤工作是交易，兩者不可混成自由文字。
5. 驗證申請、商品審核與標籤列印屬高權限管理工作；在角色、API、設備與責任尚未確認前，只做資料準備與清楚標示「未送出／待人工處理」。
6. 不可假設庫存資料完整、採收量等於標籤需求量、申請張數等於實際列印張數，也不可假設 L3 會替噴前查攔下所有不合理用藥數值。
7. 正式串接前必須取得 API 欄位／代碼字典、錯誤碼、角色權限、測試環境與版本更新方式；影片只能證明畫面與實務流程，不能取代官方規格。
