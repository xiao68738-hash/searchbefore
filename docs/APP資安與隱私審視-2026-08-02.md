# 噴前查 App 資安與隱私審視

審視日期：2026-08-02  
審視範圍：目前 Git 儲存庫、正式網站 `https://searchbefore.tw/` 的回應標頭、Firebase 前端設定、Firestore 規則、Google 登入、選用雲端同步、備份匯入、服務工作者、Android 影像辨識原型、贊助連結與隱私／刪除頁面。

## 結論先說

目前沒有在原始碼中發現私鑰、Firebase 管理員憑證、付款密鑰，亦沒有看到「任何登入者都能讀取其他使用者資料」的明顯規則。HTTP 會轉向 HTTPS，npm 套件掃描為 0 個已知漏洞。

但目前仍不適合把 L3 正式憑證或多組織資料直接接進前端。最優先要處理的是：

1. **備份匯入可形成儲存型程式碼注入的路徑。**
2. **必須到 Firebase 後台確認正式環境真的部署了儲存庫中的 Firestore 規則。**
3. **帳號及雲端資料刪除目前是寄信流程，需確認真的有可執行、可驗證身分的後台程序。**
4. **正式網站缺少 CSP、HSTS、X-Frame-Options 等回應標頭；儲存庫內的 `firebase.json` 標頭不會自動套用到 GitHub Pages。**
5. **未來 L3 介接必須由獨立後端代理，任何正式憑證都不能放進網頁或 APK。**

## 已確認的良好做法

- `firestore.rules` 採登入者 UID 與路徑 UID 相符才可讀寫，其他路徑預設拒絕。
- Google 登入與雲端同步都是選用，登入不會自動上傳田間資料。
- 雲端同步只處理 `records`、`fieldPlots`、`farmRecords` 三類資料，並有換帳號防混用邏輯。
- Google 帳號名稱、Email、頭像網址在放入 HTML 前有進行跳脫。
- OCR 已切換為 Google Cloud Vision 後端架構，前端入口暫時 `hidden`。照片只會在登入、逐次同意且正式端點啟用後送往 Cloud Run；後端會重新編碼以移除 EXIF，結果只回傳未確認草稿。Android 訊息傳遞仍保留來源白名單與 request ID 核對。
- Android OCR 原型未看到網路權限，App manifest 設定 `allowBackup=false`。
- 贊助付款僅以固定 HTTPS 連結導向綠界，前端沒有保存金流密鑰；Android／Google Play 情境也有阻擋外部綠界連結的邊界。
- 外部連結多數已使用 `rel="noopener"` 或 `rel="noopener noreferrer"`。
- 正式網址的 HTTP 會以 301 轉向 HTTPS。
- `npm audit` 結果：0 個 low、moderate、high、critical 已知漏洞。

## 發現事項與優先度

### S-01 高：惡意備份檔可能造成儲存型程式碼注入

**2026-08-03 修正狀態：已完成程式修正，待 PR 合併發布。** `readBackup()` 已改為逐欄白名單清理，限制陣列筆數、文字長度、日期、數值及 ID 格式；最近作物與商品名稱也不再直接串入 inline JavaScript，並新增惡意 ID、超量資料與失效田區測試。其餘資料驅動 inline handler 仍列為後續 CSP 收斂工作。

**證據**

- `farm-records.js` 的 `readBackup()` 只確認產品名稱、格式版本及幾個欄位是否為陣列，沒有逐筆驗證 ID、欄位長度與允許字元。
- `index.html` 會把匯入後的 `p.id`、`r.id` 等值串進 `onclick="..."`，這些位置沒有使用 JavaScript／HTML attribute 專用的安全編碼。

**風險**

使用者若讀取他人提供、遭竄改或來路不明的 JSON 備份檔，惡意 ID 可能在列表渲染或點擊時執行程式碼。攻擊程式可讀取同網域的 localStorage，因而取得田區、用藥與其他農務紀錄；若使用者已登入，也可能以該使用者身分操作前端可存取的雲端資料。

**建議**

1. `readBackup()` 對每一類資料做完整 schema 驗證、型別限制、最大筆數、字串長度與 ID 允許字元限制。
2. 不再用字串拼接產生含資料的 inline `onclick`；改用 `createElement()`、`textContent`、`dataset` 與 `addEventListener()`。
3. 匯入時重新產生內部 ID，或僅接受固定格式（例如 `^[A-Za-z0-9_-]{1,80}$`）。
4. 新增「惡意備份不得執行」的單元與瀏覽器測試。

### S-02 高（待後台確認）：Firestore 正式規則是否真的已部署

**證據**

儲存庫中的規則是合理的每使用者隔離基線，但靜態儲存庫無法證明 Firebase 正式專案目前使用的是同一版規則。

**風險**

若正式專案仍是測試模式、舊規則或誤部署，雲端田間紀錄可能被未授權讀取或寫入。

**立即確認**

- Firebase Console 的 Firestore Rules 與儲存庫 `firestore.rules` 完全一致。
- Rules Playground／模擬器驗證：未登入拒絕、A 使用者不能讀寫 B、A 可讀寫自己的允許集合、其他集合全部拒絕。
- 確認每次部署規則都有 CI／發布檢查及變更紀錄。

### S-03 高（隱私營運）：帳號與雲端資料刪除程序尚未在儲存庫中得到證明

**證據**

`delete-account.html` 目前要求使用者寄信申請，宣告 30 天處理及備份殘留最長 90 天；儲存庫中未看到管理端刪除實作、自助刪除、重新驗證身分或案件稽核流程。

**風險**

- 只提供 Email 文字不足以證明申請人控制該 Google 帳號。
- 若實際無法刪除 Firebase Authentication 帳號、Firestore 文件或無法符合宣告時程，隱私政策與實際行為不一致。
- 人工刪除若缺乏稽核，可能刪錯帳號或漏刪資料。

**建議**

1. 優先做「登入後重新驗證 → 自助刪除」流程，由可信後端以 Admin SDK 刪除 Authentication 與該 UID 下的資料。
2. 人工備援流程須用一次性驗證連結或登入驗證，不以寄件地址單獨判定身分。
3. 用測試帳號完整演練一次，保存申請時間、驗證、刪除項目、完成時間與結果。
4. 只有在確認實際備份保留機制後，才保留「90 天」等具體承諾。

### S-04 中高：正式網站缺少瀏覽器安全標頭，且沒有 CSP

**2026-08-03 修正狀態：儲存庫設定與檢查工具已完成，正式 Cloudflare 規則待設定。** `firebase.json` 已補齊 HSTS、COOP 與 CSP Report-Only；`npm run security:headers` 可檢查正式站。實測正式站仍未回傳必要標頭，需依 `docs/Cloudflare安全標頭設定.md` 完成 Cloudflare 規則後再驗證。

**實測結果（2026-08-02）**

- `http://searchbefore.tw/` 會 301 轉向 HTTPS：良好。
- `https://searchbefore.tw/` 回傳由 Cloudflare／GitHub Pages 提供。
- 回應未看到 `Content-Security-Policy`、`Strict-Transport-Security`、`X-Frame-Options`、`X-Content-Type-Options`、`Referrer-Policy`、`Permissions-Policy`。

**重要說明**

儲存庫 `firebase.json` 雖寫有部分標頭，但目前正式網站由 GitHub Pages 經 Cloudflare 提供，因此這些設定不會自動生效。

**風險**

目前頁面有大量 inline script、inline `onclick` 及 `innerHTML`。缺少 CSP 時，只要任何一處資料跳脫出錯，攻擊程式較容易執行；缺少其他標頭也會減少瀏覽器的第二層防護。

**建議順序**

1. 先完成 S-01，逐步移除資料驅動的 inline event handler。
2. 將 JavaScript 從大型 HTML 中拆出，避免依賴 `unsafe-inline`。
3. 先以 `Content-Security-Policy-Report-Only` 觀察，再逐步啟用正式 CSP。
4. 在 Cloudflare Response Header Transform Rules 或可控的正式 Hosting 設定 HSTS、nosniff、frame-ancestors／X-Frame-Options、Referrer-Policy 與 Permissions-Policy。
5. 設定後重新對正式網址實測，不只檢查儲存庫設定檔。

### S-05 中：田間資料以明文存放在瀏覽器 localStorage

**現況**

本機優先符合產品設計，也減少伺服器集中蒐集；但 localStorage 不是加密保險箱。同網域 XSS、共用電腦上的其他使用者、瀏覽器備份或裝置失竊都可能暴露資料。

**建議**

- 在個人頁清楚標示共用裝置風險，提供「清除本機資料」與匯出後刪除功能。
- 修好所有 HTML 注入路徑並啟用 CSP，優先度高於在前端自行發明加密。
- 若未來保存聯絡資料、驗證資料或 L3 憑證，不可沿用 localStorage；需改用安全後端與作業系統安全儲存。

### S-06 中：Firestore 規則只有路徑隔離，缺少資料格式與濫用限制

**現況**

規則限制集合名稱與 UID，但未限制欄位、欄位長度、時間戳、文件大小邏輯或可接受狀態。Firebase App Check 狀態也無法由儲存庫確認。

**風險**

已登入的惡意或遭竄改客戶端可以在自己的路徑寫入任意結構與大量資料，造成帳單、同步錯誤或資料完整性問題。

**建議**

- 在規則中限制必填欄位、型別、最大字串長度、不可變欄位與 server timestamp。
- 評估啟用 App Check；同時設定 Firebase 用量／預算告警。App Check 不能取代登入與規則。
- 後續多組織／L3 資料改由後端驗證，不直接相信前端寫入內容。

### S-07 中：刪除墓碑 180 天後可能讓極久未上線的裝置恢復舊資料

**現況**

雲端同步用 `_deleted:true` 防止另一台裝置把刪除資料帶回，並在 180 天後清理墓碑。

**風險**

若另一台裝置超過 180 天未同步，之後重新上線，舊紀錄可能被視為新資料重新上傳。這是資料完整性與刪除預期問題。

**建議**

使用帳號層級的同步游標／刪除世代、裝置最後同步時間與過期裝置重新確認機制；在確認安全演算法前，不只靠固定天數刪除墓碑。

### S-08 中低：隱私文字有幾處過度絕對

**現況**

隱私頁寫「只有你可以存取」等表述。Firestore 用戶端規則確實限制一般使用者，但專案管理員及受委託服務在必要情形仍具有技術處理能力。

**建議文字方向**

改成：「系統規則限制登入使用者只能透過 App 存取自己帳號下的雲端資料；僅在維運、安全事件、依法要求或依你的刪除申請所必要的範圍內，由授權人員或受委託服務處理。」同時明載雲端資料保留期限與實際刪除方式。

### S-09 低：外部程式來源與新視窗開啟仍可再收斂

- Firebase Web SDK 由 Google CDN 動態載入，無法使用一般 script tag 的 SRI。可透過建置流程固定套件版本並自家部署 bundle，降低執行期供應鏈依賴。
- `openCooperationForm()` 使用 `window.open(url, "_blank")`，雖網址是程式內固定常數，仍建議加上 `noopener` 或改用帶 `rel="noopener noreferrer"` 的 `<a>`。
- Google 登入採 local persistence；共用裝置需要明確提醒使用完畢登出。

## Firebase Web API key 的判斷

`service-config.js` 中的 Firebase Web `apiKey` 會被瀏覽器下載，本身不是管理員密鑰，不能單靠「藏起來」保護資料。真正安全邊界是：

- Firebase Authentication
- Firestore Security Rules
- Authorized domains
- API key 的 API／網站來源限制
- App Check、用量與帳單告警

本次掃描沒有發現 Private Key、Service Account JSON、ECPay 密鑰或其他伺服器秘密。仍需在 Google Cloud Console 確認該 API key 只允許需要的 API 與合法網站來源。

## L3 正式串接前的必要安全門檻

L3 不可直接從目前的靜態網頁或 APK 呼叫。正式啟用前至少要完成：

1. 可信後端代理與固定對外 IP（若農糧署要求）。
2. 憑證存入伺服器秘密管理服務，不進 Git、不進前端、不寫入紀錄。
3. 使用者與 L3 組織的強身分綁定；每次操作由後端再次判斷權限。
4. 多組織資料隔離測試；A 組織不能查詢、更新或刪除 B 組織資料。
5. 上傳、修改、刪除、產季結束的不可否認稽核紀錄。
6. 官方回應、重試、冪等與重複送件控制。
7. 權限撤銷、合作終止、帳號刪除與資安事件應變流程。
8. 最小權限、備份還原演練、監控告警與定期弱點檢查。

## 建議執行順序

### 立即（正式擴大測試前）

1. 修正備份匯入驗證與 inline onclick 注入路徑。
2. 到 Firebase 後台確認規則、Authorized domains、API key 限制、App Check 與預算告警。
3. 用兩個測試帳號執行跨帳號存取測試。
4. 用測試帳號演練完整刪除，修正刪除頁與隱私頁不一致之處。
5. 在 Cloudflare 加入安全標頭；CSP 先使用 Report-Only。

### 近期（公開測試期間）

1. 將大型單頁 HTML 的 script、style 與事件逐步拆出。
2. 為備份、同步、刪除與登入加入安全回歸測試。
3. 設定 Firebase／Cloudflare 異常流量、錯誤與預算告警。
4. 建立資安事件處理清單：停用同步、撤銷金鑰、通知使用者、保全紀錄與修復發布。

### L3 開發前

1. 完成後端威脅模型與資料流圖。
2. 決定正式主機、固定 IP、Secrets Manager、資料庫及備份方案。
3. 定義農民、登打員／資訊服務專員、組織管理者及開發維運者的權限矩陣。
4. 取得農糧署規格後再做 API 欄位與操作權限，未完成前保持前端隱藏或明確標示開發中。

## 本次未能只靠原始碼確認的項目

- Firebase Console 實際部署中的 Rules、App Check、Authorized domains 與 API key 限制。
- Google Cloud／Firebase 管理員名單及是否啟用多因素驗證。
- Cloudflare 帳號安全、DNSSEC、WAF／Bot／Rate Limit 設定。
- GitHub 儲存庫權限、分支保護、Secret scanning、Dependabot 及管理員 MFA。
- 刪除申請是否有實際後台 SOP 與執行人。
- Android 正式 AAB 與 Play Console Data safety 宣告是否與目前程式一致。
- L3 尚未取得的正式 API 驗證、網路與稽核要求。

這些項目應以後台截圖、測試帳號與實際操作逐項驗證，不能因儲存庫內有設定檔就視為已完成。
