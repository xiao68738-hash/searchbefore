# L3 介接申請與上線流程備忘

更新日期：2026-08-02

這份文件用來記住「找到合作農民之後，產銷履歷 L3 API 要怎麼一路做到正式啟用」。內容依農糧署承辦窗口的書面答覆整理；實際技術規格與驗收方式，仍以申請核准後取得的文件為準。

## 一句話版本

先找一位**已通過產銷履歷驗證、願意合作測試的農產品經營者**，確認他的 L3 組織資料並共同送出介接申請；農糧署核准後才會提供技術文件與測試環境，完成開發、測試及正式環境設定後，其他有 L3 組織代碼的經營者就能使用，不必每人重新申請一次系統介接。

## 名詞白話說明

- **農產品經營者**：可能是個別驗證農民，也可能是產銷班、農場或法人團體。個別驗證與集團驗證都可以屬於農產品經營者。
- **L3 組織代碼**：產銷履歷系統辨認「這筆資料屬於哪一個農產品經營者」的組織編號。它不是一般網站帳號，也不能只靠履歷標籤頁面自行猜測。
- **第一位測試對象**：介接申請時用來證明有真實需求、配合測試的已驗證農產品經營者。依承辦窗口答覆，個別驗證農民也可作為合作對象，無須一定是產銷班。
- **系統介接申請**：是「噴前查這套工具」申請取得 API 測試資格；不是每一位未來使用者都要重新申請同一套介接。

## 完整流程

### 1. 找到願意合作的已驗證農民或團體

先確認對方願意：

1. 提供 L3 主機中的組織名稱與組織代碼。
2. 讓噴前查以其身分作為第一位 API 測試對象。
3. 核對預填的申請書並在需要的位置簽章。
4. 在測試階段提供少量、去識別化或測試用紀錄，協助核對結果。

不要把空白申請書直接交給農民研究。應由開發者先填妥技術與系統欄位，再請農民確認自己的資料及簽章。

### 2. 確認對方是否具備 L3 組織資料

最可靠的確認方式，是請對方登入產銷履歷資訊管理系統，查看或向其驗證機構／系統客服確認「L3 組織名稱及代碼」。公開履歷頁、標章號碼或栽培批次畫面只能證明有履歷資料，不能單獨證明申請書所需的 L3 組織代碼。

需要記下：

- L3 組織名稱
- L3 組織代碼
- 驗證型態（個別驗證或集團驗證）
- 聯絡人與聯絡方式
- 願意配合測試及簽章的確認

### 3. 先向承辦窗口確認五個尚未定案的問題

寄出申請書前，以短訊息或郵件確認：

1. 個人開發者能否填寫「系統開發單位名稱」？應使用本名、商號名稱或其他寫法？
2. 「連線電腦 IP」是否必須是固定的後端對外 IP？
3. 測試環境與正式環境能否使用不同 IP？
4. 申請書應以電子檔、紙本或兩者送件？需要哪些簽章？
5. 個別驗證農民能否作為第一位測試對象？

在取得答覆前，不購買或承諾特定伺服器方案，也不自行假設 IP、簽章或送件規則。

### 4. 預填申請書並與合作農民核對

開發者負責：

- 系統名稱、用途、開發單位與聯絡資料
- 預計申請的下載、維護、刪除、產季結束等 API
- 測試與正式環境的網路／IP 資料
- 安全與權限管理說明

合作農民負責：

- 確認組織名稱及 L3 組織代碼正確
- 確認願意作為第一位測試對象
- 在農產品經營者欄位核對並簽章

### 5. 送件、補件與審核

送交農糧署指定窗口後，等待審核或補件通知。申請不等於已取得正式串接資格；在核准前，噴前查前端不能宣稱「已可直接上傳產銷履歷」。

依承辦窗口答覆，原則上所有需要使用的 API 都要提出申請，但最終實際開放項目仍由農糧署審核決定。

### 6. 核准後取得技術資料與測試環境

核准後才會取得可用來評估與開發的資料，例如：

- WSDL 或 API 規格
- 測試環境網址與驗證方式
- 作物、品種、作業、肥料、病蟲害防治對象等官方代碼下載方式
- 欄位限制、錯誤碼與回傳格式
- 測試資料與驗收要求

所有官方代碼都應透過核准後的 API 取得，不自行建立看似相同的正式代碼表。

### 7. 建立安全的後端介接層

正式 API 憑證、密鑰或固定 IP 介接不能放在 GitHub Pages、瀏覽器 JavaScript 或 Android APK 中。建議架構為：

`使用者 App／網頁 → 噴前查後端 → 農糧署 L3 API`

後端至少需要：

- 使用者及 L3 組織的身分綁定
- 每個組織各自的授權與資料隔離
- 憑證／密鑰的伺服器端保管與輪替
- 固定對外 IP（若承辦窗口確認需要）
- 上傳前欄位驗證與官方代碼轉換
- 操作稽核紀錄、失敗重試與回傳收據
- 刪除、修改及產季結束等高風險操作的再次確認

### 8. 在測試環境完成整套情境

至少測試：

- 官方代碼下載與更新
- 新增、修改、刪除生產紀錄
- 產季結束
- 無效代碼、缺漏欄位與重複送件
- 網路中斷、逾時、重試及避免重複寫入
- 不同 L3 組織之間無法互看或誤傳資料
- App 顯示的成功狀態與 L3 實際回應一致

只收到「已送出」不能當作「官方已收件成功」。畫面必須區分等待送出、送出中、官方接受、官方拒絕及待人工處理。

### 9. 配合農糧署完成介接測試與驗收

實際需要哪些測試案例、文件、截圖或共同測試，必須依核准後提供的規範執行。沒有取得規格前，不自行承諾確切驗收步驟或時程。

### 10. 切換正式環境並小量上線

正式憑證、正式端點與 IP 白名單完成後，先讓第一位合作對象小量試用，逐筆核對 App、噴前查後端及 L3 系統三方結果。確認穩定後，再逐步開放其他農產品經營者。

其他經營者不必重新申請「噴前查的系統介接」，但每位經營者都要有自己的 L3 組織代碼，並完成噴前查內的身分綁定與授權。

## 現在最先做的事

1. 找到一位已驗證且願意測試的個別農民或團體。
2. 請對方確認 L3 組織名稱與代碼，不要只看公開履歷頁推測。
3. 寄出五題確認信。
4. 收到答覆後，由開發者預填完整申請書，再交給農民核對與簽章。
5. 在 API 正式核准前，先完成不依賴 L3 的紀錄、匯出、影像辨識草稿與安全架構準備。

## 重要界線

- 現有「本機紀錄／匯出」功能不等於 L3 串接。
- 未核准前不要在前端顯示可直接上傳產銷履歷。
- 未完成的介接功能應隱藏；若為測試展示，必須清楚標示「開發中／不會送出正式資料」。
- 農民、登打員或資訊服務專員應被設計為覆核者與協作者，而不是被系統默默取代。
- L3 正式資料涉及生產紀錄與組織權限；正式商用前必須另做後端、權限、稽核、刪除及事件應變設計。
