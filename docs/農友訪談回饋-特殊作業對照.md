# 農友訪談回饋：官方選項以外的特殊作業

更新日期：2026-08-02  
狀態：已建立內部安全狀態模型與單元測試；尚未取得官方代碼表、完成真實案例訪談或決定正式功能，不得出現在正式前端。

## 一、去識別化回饋摘要

農友認同「拍照後協助登打」的方向，但指出：真正的問題不一定只是把紙本內容辨識成文字，而是部分實際農務作業在產銷履歷系統內沒有可直接選擇的項目。

實例：農友為了防止動物危害，進行「捕捉飛入設施內的大型蝙蝠」等特殊作業。現行操作方式可能是在官方系統選擇「其他」，再自行填寫備註。

為保護訪談對象隱私，本文件不保存對話截圖、姓名、頭像或帳號。

## 二、這項回饋代表什麼

### 1. OCR 只能解決「看見文字」，不能解決「官方欄位沒有選項」

即使照片辨識完全正確，系統仍可能找不到相符的官方作業代碼。因此辨識功能不能把自由文字強迫歸入最相近的分類，否則會製造看似完整、實際錯誤的正式紀錄。

### 2. 必須同時保存兩層資料

- **現場原始事實**：農民實際做了什麼，保留其原始說法。
- **官方登打表示**：官方系統所選類別、代碼及備註內容。

兩者不可互相覆蓋。若官方只有「其他」，噴前查仍應保留原始作業文字，並清楚標示尚未找到一對一官方項目。

### 3. 登打人員的價值反而更明確

特殊、地方性或低頻作業需要熟悉制度的人判斷應選哪個官方項目以及如何備註。噴前查可以整理候選與原始依據，但最後仍由人確認，符合「增效而非取代」的產品定位。

### 4. 最新回饋：即使先辨識，登打人員仍須逐筆查看

訪談對象進一步指出，紙本紀錄與產銷履歷系統的欄位及操作並不同步；即使先把照片中可確認的內容整理出來、把不確定內容放入備註，登打人員仍可能需要逐筆查看。

這段回饋目前只能證明「這位受訪者認為逐筆檢查無法省略」，不能直接推論所有登打人員的流程都相同，也不能推論預填完全無法節省時間。下一步必須觀察真實登打流程，分辨時間究竟花在：

- 看懂紙本或手寫內容。
- 判斷紙本內容應對應哪個官方欄位或選項。
- 操作官方系統、重複輸入共同資料。
- 查缺漏、回頭詢問農民或修正錯誤。

因此產品目標不再設定為「免除逐筆檢查」，而是「保留逐筆確認責任，同時減少每筆資料的閱讀、查找、重打與遺漏」。

## 三、建議的資料狀態

每筆特殊作業至少需要保存：

| 欄位 | 用途 |
|---|---|
| `sourceText` | 農民原始說法，不自動改寫 |
| `normalizedActivity` | 經人工確認後的標準化描述 |
| `officialCode` | 官方代碼；尚無對應時為空 |
| `mappingStatus` | `exact`、`suggested`、`other` 或 `unmapped` |
| `officialNote` | 預計填入官方系統備註的內容 |
| `reviewer` / `reviewedAt` | 誰在何時確認對照 |
| `sourceVersion` | 原始內容修訂時，使舊的確認結果失效 |

正式狀態名稱及欄位仍須等 L3 代碼表與 API 規格取得後決定，現在不得自行建立看似官方的代碼。

## 四、未來介面方向

在正式規格與試辦完成前不建立公開入口。未來可以評估：

1. 農民輸入、拍照或語音留下原始作業。
2. 系統只提出「可能對應項目」，同時提供「找不到合適項目」。
3. 找不到時保留為「待人工對照」，不得自動選最接近的項目。
4. 登打人員查看原始內容、建議類別與備註草稿。
5. 人工確認後，才產生 TAP 登打對照內容。
6. 若官方允許使用「其他＋備註」，介面要同時顯示官方類別與完整原始作業，不可只剩「其他」。

若試辦證實仍須逐筆處理，優先評估的不是批次自動送出，而是「逐筆覆核工作台」：

- 同一畫面並列原始照片、辨識文字與預計登打欄位。
- 不確定欄位逐一醒目標示，不把不確定內容一律塞入備註。
- 共同欄位可沿用上一筆，但每筆仍保留確認動作。
- 提供複製、下一筆、退回補充及已確認標記，減少畫面往返。
- 保存原始依據、修改紀錄、確認人與時間，不自動送入 L3。

## 五、下一輪訪談問題

不急著先做更多 OCR，先向 5～10 位農民或登打人員蒐集：

1. 哪些實際作業在官方系統中找不到選項？
2. 目前是選「其他」、選相近項目，還是乾脆不登錄？
3. 備註通常怎麼寫？是否有產銷班或驗證機構的固定做法？
4. 哪些情況最容易因選項不足而被退件或要求補充？
5. 不同作物、設施與地區是否有不同的特殊作業？
6. 登打人員希望系統提供候選分類、自由文字，還是兩者並列？
7. 所謂「仍要一筆一筆看」，每筆實際要檢查哪些內容？
8. 如果欄位已依官方系統順序預先整理，逐筆確認會變快、相同，還是更慢？
9. 同一批資料有哪些欄位通常相同，可以安全沿用但仍由人確認？
10. 能否以去識別資料觀察或錄下 5～10 筆實際登打，量測各步驟時間與修正原因？

每個案例應記錄「原始作業、目前官方登法、誰確認、是否曾被要求修改」，但不得蒐集 L3 密碼或把含個資的聊天截圖放入公開儲存庫。

## 六、產品優先級判斷

這項問題應排在「大量訓練任意表單 OCR」之前先驗證。OCR 改列為輸入輔助，逐筆覆核工作台與紙本／官方欄位差異盤點列為第一優先。原因是：

- OCR 做得再準，也無法補出不存在的官方選項。
- 特殊作業對照會直接影響資料是否如實及能否上傳。
- 蒐集真實例外案例，可同時改善表單設計、登打工作台與未來 L3 對照層。
- 即使人工確認不能取消，只要能可靠降低每筆處理時間、漏填率或來回詢問次數，仍可能具有商業價值；但必須以實測證明。

內部模型 `tap-activity-mapping.js` 已固定以下安全語意：保留農民原文、候選不等於確認、官方項目只接受核准後由 API 取得的代碼表、只有人工覆核能確認正式對照，以及原文修訂後舊對照立即失效。它不連接 L3，也未進入正式 build。

目前下一步仍是蒐集例外案例、盤點紙本與官方欄位差異，並觀察逐筆登打流程，不是發布新功能。正式 APP 不顯示 OCR、自動匯入或登打工作台入口；在實測證明有效以前，也不對外宣稱可以省去逐筆確認。
