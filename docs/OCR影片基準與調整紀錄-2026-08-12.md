# OCR 影片基準與調整紀錄

更新日期：2026-08-12
狀態：測試基準；不得自動儲存、不得宣稱可直接上傳 L3

## 1. 基準來源

本次以三類資料交叉整理，不以單一 OCR 輸出或單一畫面推定需求：

1. 目前 `origin/main` 的 OCR 實作、規格與自動測試。
2. 匿名化 OCR golden fixtures：自我查核表、表 10 資材庫存、表 18 設備管理。
3. 2026-08-07 錄製的 39 分 03 秒產銷履歷系統操作影片及其音訊。

原始影片、擷取畫面、WAV 與逐字稿可能含帳號、姓名、電話、地號或其他個資，只保存在工作區的 `ocr-video-analysis`，不得加入公開 Git。本文只保留去識別化的流程結論與時間點。

## 2. 現有 OCR 能力基準

目前已具備：

- 照片品質閘門、來源識別、請求 ID 與大小上限。
- 多張照片各自排隊、辨識、成功或失敗，不跨照片拼接資料。
- 文件先分流，再進入生產紀錄、設備管理、資材庫存或備查流程。
- 保留頁次、列、儲存格及文字區塊證據；跨頁與跨區域不得只因高度相近而合併。
- 一張照片可建立零至多筆候選；候選必須逐筆、逐欄人工確認。
- 表 10 維持資材主檔與進出庫明細的兩層結構；空白不得補成零。
- 表 18 可拆多筆日期、設備與作業；不把相鄰頁的採後內容混入。
- 自我查核表只供備查，不建立田間作業。
- 所有 OCR 草稿皆為 `autoCommitAllowed=false`、`l3UploadReady=false`。

尚未完成的基準缺口：

- 真實照片仍只有匿名化文字／幾何 fixtures，缺少經同意保存的原圖測試庫。
- 尚未量測文件分類正確率、必要欄位正確率、人工修改數與總省工時間。
- 生產紀錄的施肥、採收、採後處理仍需更完整的專用覆核介面。
- 正式 L3 字典、角色、測試環境與 API 規格尚未取得。

## 3. 影片與音訊整理

### 3.1 主要流程時間軸

| 約略時間 | 畫面與音訊重點 | OCR／產品含意 |
|---|---|---|
| 00:00–04:10 | 登入、選擇經營者與既有栽培紀錄 | 帳號、經營者及農民不可由 OCR 自行推定；個資不得進公開測試資料。 |
| 04:10–07:00 | 選擇農民、栽培批次與驗證田區；同一作業排程的地號會另以 H／B 等工作區概念整理 | 「地號／驗證田區」與「實際共同作業分區」是不同層次，不得因代號相似而自動合併。 |
| 06:30–07:00 | 反覆登打對不熟悉鍵盤的使用者負擔高 | OCR 價值應以減少人工修改數和總登打時間衡量，不以辨識成功畫面衡量。 |
| 07:00–12:30 | 新增栽培工作；施肥分基肥、追肥等，肥料資料有時較自由 | 先判斷紀錄類型；肥料名稱不得硬套農藥的正式登記邏輯。 |
| 12:30–19:30 | 防治資材選擇、用量、水量與稀釋倍數；實際使用倍數可能與畫面建議值不同 | OCR 必須分開「本次實際使用」與「標示／建議」倍數，建議值不得自動寫成施用紀錄。 |
| 19:30–21:10 | 以既有紀錄複製，再修改本次資料 | 後續可評估「確認共同欄位後複製草稿」，但不可跳過逐筆核對或建立重複紀錄。 |
| 21:10–25:30 | 採收、包裝重量、標籤張數及可用數量關聯 | 採收量、包裝規格與標籤張數屬不同欄位；不得只由總公斤數自動推定標籤需求。 |
| 25:30–32:00 | 商品、驗證及其他管理畫面 | 高權限管理資料維持 `admin-output`／唯讀說明，不建立生產紀錄。 |
| 32:00–38:00 | 商品規格、QR 標籤版型、列印與重量責任 | 標籤列印另立安全流程；重量或張數錯誤可能有實際責任，不納入目前 OCR 自動化。 |

### 3.2 音訊證據形成的規則

1. 同一共同作業區可能涵蓋多個正式地號；OCR 只提供兩者候選，不自行建立一對多關聯。
2. 農民實際操作資料優先於畫面推薦資料，但仍需人工核對原始紀錄。
3. 重複登打確實是痛點；可提供草稿複製或共同欄位套用，但必須保留來源、日期與去重檢查。
4. 包裝重量、採收量、標籤張數及剩餘可用量不可互相臆測。
5. OCR 的完成定義是省工且不增加錯誤，不是「有抓到文字」。

## 4. 本次功能調整

### 稀釋倍數語意分流

`findDilutions()` 現在為每個倍數候選加入：

- `role=actual`：前文標示實際、本次、施用、使用、調配或配製；可達預選信心門檻。
- `role=unlabeled`：只有倍數而無用途；保留候選，但介面清楚標示用途未明。
- `role=reference`：前文標示建議、推薦、標示、標籤、登記或參考；信心刻意低於預選門檻，必須人工選擇。

候選排序為實際值、未標示值、建議值。相同倍數重複出現時只保留語意較強的候選。介面仍以純數值作為欄位值，但另外顯示角色說明，避免把標示建議值誤當成本次施用值。

### 位置資料分流

位置候選現在分成三種角色：

- `officialField`：明確標示為正式田區、驗證田區或田區代號，才可出現在田區候選。
- `workGroup`：共同作業分區、工作區或管理分區，只保留供人工核對，不自動匹配正式田區。
- `landParcel`：地號或地籍號碼，只作來源證據，不自動建立田區關聯。

因此只寫「H 區」或「B 區」而沒有正式田區標籤時，不再自動當成可帶入的田區代號。

### 採收量、包裝與標籤分流

採收相關數值現在分成：

- `harvestQuantity`：本次採收量或總採收量；採收文件只將此角色放入一般數量候選。
- `packageWeight`：每包重量、包裝重量或包裝規格；只顯示供核對。
- `labelCount`：標籤、貼紙或列印張數；只顯示供核對。

系統不以採收量除以包裝重量推算標籤張數，也不以標籤張數反推採收量。三類候選都保留在標準多筆草稿中，以便逐筆追溯來源，但只有採收量可進入採收數量欄位。

## 5. 驗收基準

- 同時出現「建議 2,000 倍」及「本次實際使用 1,000 倍」時，1,000 倍排在前面且可預選；2,000 倍不得自動預選。
- 只有建議值時仍可供人工選擇，但不自動帶入。
- 相同倍數以建議與實際兩種語意重複出現時，只保留實際候選。
- 共同作業分區與地號不得出現在正式田區候選中。
- 同時出現採收量、包裝規格與標籤張數時，採收數量欄位只包含採收量。
- 原有 OCR 核心、UI、golden fixtures、完整測試與 release check 必須全部通過。

## 6. 下一批優先工作

1. 在取得同意後補齊真實原圖測試庫，原圖存放於非公開、具權限與保存期限的資料區。
2. 分開「正式地號／田區」與「共同作業分區」候選，禁止自動合併。
3. 對已確認草稿增加共同欄位套用與重複偵測，量測是否真的縮短登打時間。
4. 補施肥、採收與採後處理的專用覆核介面。
5. 標籤、重量與高權限管理功能維持 OCR 範圍外，直到取得正式規格與責任流程。
