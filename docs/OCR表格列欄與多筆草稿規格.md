# OCR 表格列欄與多筆草稿規格

更新日期：2026-08-10

狀態：測試中；不得自動儲存、不得宣稱可直接上傳 L3

## 1. 要解決的問題

產銷履歷紀錄本常以整頁或跨頁方式拍攝，一張照片可能同時包含：

- 印刷表頭與說明文字；
- 多列手寫日期、資材、數量或設備作業；
- 勾選框、空白列及報紙等背景文字；
- 左右兩頁或同頁多個獨立小表格。

單純把所有文字串成一段，無法判斷哪個日期與哪筆數量屬於同一列。因此系統須先保留文字位置，再產生「可能同列」的幾何候選，最後才由紀錄類型解析器整理成多筆待確認草稿。

## 2. 分層原則

### 2.1 雲端辨識層

只負責輸出印刷／手寫文字、信心及標準化座標。不得猜測農務語意，也不得把某列直接標為「已完成施肥紀錄」。

### 2.2 幾何結構層

依頁次、文字垂直重疊與水平空隙產生列與儲存格候選。候選只表示空間關係，不表示欄位正確。

### 2.3 文件解析層

先判斷文件類型。只有類型明確時，才以該類型的已知欄位尋找可能的日期、資材、數量等；不確定或衝突時必須保留為人工選擇。

### 2.4 人工核對層

使用者逐張、逐筆對照原圖。低信心或缺必要欄位的候選不得預選，也不得直接寫入正式紀錄。

## 3. 幾何候選資料

每個候選至少保留：

- `pageIndex`：OCR 頁次；
- `rowCandidateId`：本次回應中的列識別碼；
- `box`：標準化 `left/top/right/bottom`；
- `text`：有長度上限的候選文字；
- `confidence`：來源文字的保守彙整信心；
- `cellCandidates[]`：由水平空隙切出的候選片段；
- `wordIds[]`：可回查原始 OCR 單字與座標；
- `truncated`：是否因安全上限而截斷。

同一列不等於同一筆農務紀錄。左右兩頁、跨欄表格及背景文字必須保持不同來源，不得因 Y 座標接近而合併。

## 4. 標準中介草稿

OCR 草稿使用 `activities[]` 表示一張照片內的零至多筆候選活動。每一筆至少包含：

```json
{
  "id": "activity-1",
  "kind": null,
  "kindCandidate": "equipmentMaintenance",
  "route": "supporting-record",
  "destination": "farm-form",
  "associationState": "row-evidence",
  "status": "pending-confirmation",
  "confidence": 0.72,
  "source": {
    "sourceImageId": "ocr-source-...",
    "rowCandidateIds": ["row-1"],
    "cellCandidateIds": ["row-1-cell-1"],
    "blockIds": ["cloud-3"]
  },
  "details": [],
  "confirmation": { "state": "pending", "confirmed": false },
  "l3MappingStatus": "not-mapped",
  "mappingPending": true,
  "l3UploadReady": false,
  "autoCommitAllowed": false
}
```

規則：

- 未辨識到的值使用 `null` 或空候選，不得由系統臆測補值。
- 欄位候選須保留來源、信心與 `confirmed: false`。
- `activities[]` 只供核對，不代表可以儲存或上傳。
- 所有陣列與文字皆設上限，避免大型文件耗盡手機記憶體。

## 5. 兩類優先案例

### 5.1 器具／機械／設備管理紀錄

一列可能包含一個日期、多個設備勾選及多個作業勾選。第一階段不得把多個設備與多個作業直接做笛卡兒積組合；應先保存同列候選，由使用者確認哪些設備與作業實際相配。

必要確認：日期、至少一項設備、至少一項作業內容。記錄人看不清楚時可以留空並顯示警告。

### 5.2 肥料／資材入出庫紀錄

表頭的資材名稱、廠商、供應商、包裝單位與容量，和下方多列日期／購入量／使用量／剩餘量屬主表加明細結構。

第一階段輸出：

- 一個資材主表候選；
- 零至多個庫存明細候選；
- 每個明細保留同列來源，不以全文中的第 N 個日期強配第 N 個數量。

在欄位位置尚未可靠對應以前，只能下載或人工整理草稿，不得直接帶入正式田間紀錄。

## 6. UI 流程

1. 一次加入一張或多張照片。
2. 每張照片顯示等待、處理中、完成或失敗。
3. 完成後顯示該照片辨識到的候選筆數。
4. 使用者選一筆候選，畫面顯示其原圖來源與待確認欄位。
5. 缺欄或低信心值保持未勾選。
6. 使用者可略過、修改或確認；單筆錯誤不影響其他照片。
7. 通過「可帶入人工整理」門檻後，才可開啟既有表單。
8. 既有表單的類型必填驗證通過後，才可由使用者主動儲存。

## 7. 隱私與安全

- 草稿只保存來源識別碼與位置證據，不保存原始照片、Object URL、Base64 或 `File` 物件。
- 前端不顯示內部服務供應商名稱；隱私權政策仍須正確揭露第三方資料處理。
- 後端不記錄原圖、全文、驗證碼或登入 token。
- 真實照片不得直接加入公開測試資料；測試 fixture 必須匿名化並移除姓名、電話、地址與地號。

## 8. 驗收條件

- 旋轉雙頁照片不會把左右頁同高度文字錯合成單列。
- 一張設備表可產生多列候選，且每列能回查原圖位置。
- 一張肥料入出庫表可區分主表與多列明細，不以全文順序硬配欄位。
- 背景報紙文字不會自動成為可儲存紀錄。
- 類型不明、第一二名分數接近或缺必要欄位時，只能人工整理。
- 多圖中任一張失敗，不會清除其他成功草稿。
- 完整測試與發布檢查通過，且正式前端持續標示「測試中」。
