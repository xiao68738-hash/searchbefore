# 田區摘要與作業導引：實作規格

本文件承接《產品深化但不增加介面複雜度-架構設計》。目前只定義架構與驗收條件，不代表功能已上線。

## 1. 產品目標

使用者開啟「紀錄」時，不需要先翻找多個頁面，就能回答：

1. 目前正在看的田區是哪一塊？
2. 最近一次留下了什麼紀錄？
3. 目前安全採收狀態如何？
4. 下一步要按哪裡？

這四個答案集中在一張摘要卡；完整資料仍留在既有的田區詳細頁、倒數頁與匯出頁。

## 2. 分層設計

```text
資料層
  localStorage / 現有 store
      ↓
領域層（不碰 DOM）
  record-normalizer.js
  field-summary.js
  action-resolver.js
      ↓
呈現層
  record-summary-card.js
      ↓
既有頁面
  recordHubHome / plotDetailModal / harvest screen
```

### 2.1 `record-normalizer.js`

用途：把用藥紀錄與農務紀錄轉成共同的事件格式，讓後續模組不用知道不同資料結構的細節。

輸入：

- `records`：用藥紀錄。
- `farmRecords`：栽培、施肥、採收、採後、資材購入、設備保養等紀錄。
- `fieldPlots`：田區與種植批次。

輸出事件格式：

```js
{
  id: "source-id",
  plotId: "plot-id-or-null",
  date: "YYYY-MM-DD",
  kind: "pesticide | cultivation | fertilizer | harvest | postharvest | materialPurchase | equipment",
  label: "施肥",
  summary: "苦土石灰 15 包",
  source: "pesticide | farm",
  sourceRef: "original-record-id",
  quality: "normal | incomplete | invalid"
}
```

規則：

- 原始欄位不直接改寫。
- 日期無效時保留事件，但標記 `invalid`，不可作為最近作業排序依據。
- `plotId` 空值不可猜測歸屬到同作物的田區。
- 設備保養等共用設備紀錄可保留 `plotId = null`，在田區摘要中只顯示為「共用設備最近紀錄」，不可誤算成該田區已完成作業。

### 2.2 `field-summary.js`

用途：針對一個田區產生可供 UI 顯示的狀態快照。

```js
buildFieldSummary({
  plot,
  events,
  pesticideRecords,
  today
})
```

回傳：

```js
{
  plot: { id, displayName, crop, plantDate },
  activity: {
    latest: { date, label, summary } | null,
    count: number,
    byKind: { pesticide, cultivation, fertilizer, harvest, postharvest, materialPurchase, equipment }
  },
  safety: {
    status: "safe | waiting | unknown | none",
    safeDate: "YYYY-MM-DD" | null,
    daysRemaining: number | null,
    consideredRecords: number,
    missingPhiRecords: number
  },
  dataQuality: {
    invalidDateCount: number,
    unlinkedEventCount: number
  }
}
```

安全狀態必須使用現有安全採收計算；不得在本模組複製另一套 PHI 規則。

### 2.3 `action-resolver.js`

用途：把狀態轉成「只顯示一個」的行動建議。

```js
resolveNextAction(summary)
```

輸出：

```js
{
  code: "CREATE_PLOT",
  label: "先建立第一個田區",
  detail: "有了田區後，後續紀錄才容易分開整理。",
  target: "plots",
  priority: 1
}
```

建議優先序：

| 優先序 | 條件 | 行動代碼 | 說明 |
|---:|---|---|---|
| 1 | 沒有任何田區 | `CREATE_PLOT` | 建立田區是其他紀錄的基礎 |
| 2 | 有用藥但部分沒有安全採收期 | `REVIEW_SAFETY` | 進入既有倒數頁核對標示 |
| 3 | 仍在停採期 | `VIEW_COUNTDOWN` | 查看最晚可採日期 |
| 4 | 田區沒有任何事件 | `ADD_FIRST_RECORD` | 進入既有農務紀錄入口 |
| 5 | 有事件但最近沒有農務紀錄 | `CONTINUE_RECORD` | 繼續留下實際作業 |
| 6 | 有可整理資料 | `EXPORT_RECORDS` | 進入既有匯出功能 |

不加入「建議施什麼藥」「建議施多少肥」「建議何時採收」等行動。

## 3. 田區選擇服務

### `selectSummaryPlot()`

```js
selectSummaryPlot({ fieldPlots, activePlotId, events })
```

選擇順序：

1. `activePlotId` 對應到仍存在的田區。
2. 最近有有效日期事件的田區。
3. 最近建立的田區。
4. 沒有田區則回傳 `null`。

若 `activePlotId` 已被刪除，服務只能選擇替代田區，不能自動寫回新的預設值。是否改變預設田區必須由使用者按下既有「設為預設」。

## 4. 介面規格

### 4.1 位置

摘要卡放在 `recordHubHome` 內、三個入口按鈕之前。三個入口的文字、順序、操作方式不變。

### 4.2 卡片內容

正常情況：

```text
目前田區
番茄・A區

最近作業       2026/08/06・施肥
安全採收       還有 5 天，2026/08/12 起可採

[查看田區]
```

資料不足：

```text
目前還沒有可整理的田區紀錄
先建立田區，之後用藥與農務紀錄會集中在同一條時間軸。

[建立田區]
```

狀態不明：

```text
安全採收       目前無法判定
有 1 筆用藥缺少安全採收期，請回到倒數頁核對產品標示。

[查看倒數]
```

### 4.3 視覺限制

- 使用現有 `record-hub` 色彩與圓角，不新增另一套卡片風格。
- 一張卡最多兩行狀態與一個主要按鈕。
- 不顯示完整時間軸、所有紀錄數量或多個次要按鈕。
- 不使用紅色代表「有錯誤」；只有確定資料不足時才使用既有 `unknown` 警示色。
- 小螢幕、特大字與深色模式必須支援換行。

## 5. 點擊行為

| 行動代碼 | 點擊後位置 | 不應做的事 |
|---|---|---|
| `CREATE_PLOT` | 開啟既有田區新增／管理面板 | 不自動新增空白田區 |
| `REVIEW_SAFETY` | 開啟安全採收倒數 | 不直接把資料標成安全 |
| `VIEW_COUNTDOWN` | 開啟安全採收倒數並保留田區脈絡 | 不跳出新的設定流程 |
| `ADD_FIRST_RECORD` | 開啟農務與設備紀錄 | 不自動填入作業內容 |
| `CONTINUE_RECORD` | 開啟農務與設備紀錄 | 不猜測使用者要記錄的類型 |
| `EXPORT_RECORDS` | 開啟匯出頁 | 不自動下載檔案 |

## 6. 資料安全與隱私邊界

- 摘要在本機計算，不新增網路請求。
- 不把衍生摘要存進雲端，也不新增使用者追蹤資料。
- Google 登入仍只是選用的同步機制，不因開啟摘要而強迫登入。
- 摘要卡不得顯示完整地籍、電話、地址等不必要欄位。
- 匯出內容沿用既有匯出權限與使用者主動操作，不在背景自動產出檔案。

## 7. 未來擴充但先不實作

### 7.1 同步層

若日後啟用雲端同步，摘要服務仍應以「資料來源介面」注入資料：

```js
buildFieldSummary({
  fieldPlots: dataSource.getFieldPlots(),
  pesticideRecords: dataSource.getPesticideRecords(),
  farmRecords: dataSource.getFarmRecords()
})
```

如此可保持摘要規則與本機／雲端來源分離。雲端資料版本衝突時，先顯示「資料同步中」或「請確認最新版本」，不可靜默覆蓋本機資料。

### 7.2 提醒層

未來如加入通知，只能從摘要的明確狀態產生：

- 可採日期即將到來。
- 有資料無法判定。
- 使用者自行設定的紀錄提醒。

不根據「很久沒使用」推測農民忘記作業，也不把通知當成法規提醒。

### 7.3 匯出層

摘要不直接生成新的報表格式。若日後需要「田區摘要報表」，應沿用現有完整匯出資料與欄位說明，並標註「整理摘要，不代表驗證通過」。

## 8. 驗收條件

在進入前端實作前，架構必須通過：

1. 所有既有安全採收測試不變且通過。
2. 同一田區多筆用藥時，摘要顯示最晚可採日。
3. 其中一筆缺少 PHI 時，摘要顯示「無法判定」。
4. 同作物不同田區不可因作物名稱相同而混合。
5. 設備共用紀錄不會被計入某一田區的農務完成度。
6. 沒有田區、沒有紀錄、失效預設田區都能顯示可理解的狀態。
7. 任何狀態只產生一個主要行動。
8. 不新增資料上傳、不新增登入要求、不新增追蹤欄位。
9. 不改變既有三個紀錄入口及現有詳細頁操作。
10. 390px 寬度、特大字、深色模式下摘要卡不遮住底部導覽。

## 9. 開發順序

1. 先寫 `record-normalizer` 與 `field-summary` 的純函式測試。
2. 再寫 `action-resolver` 的優先序測試。
3. 以假資料產生文字版摘要，人工檢查是否會誤導。
4. 最後才加入一張摘要卡的 UI。
5. 真實農民測試時，只問「你知道下一步按哪裡嗎？」與「這張卡有沒有幫你少找頁面？」。

如果使用者仍然需要閱讀說明才能理解摘要卡，就代表摘要太複雜，應刪內容，不應再加教學。
